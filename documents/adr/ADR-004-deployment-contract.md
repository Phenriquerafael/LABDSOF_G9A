# ADR-004 — Deployment contract, environments and pipeline

**Status:** Proposed
**Date:** 2026-11-01
**Participants:** Ricardo (P2, Tech Lead) — proposer; Martim (P5, DevOps) to confirm; team review pending
**Related decision:** DEC-04
**Supersedes / superseded by:** revises in place the 2026-10-15 version (nginx edge, about six to eight containers); see [Record](#record)

## Context

The topology has three hosts (listed below). The **application host** runs twelve services: traefik, client, issue, dispatch, notification, keycloak, ai-triage, calendar-sim, rabbitmq, mailpit, prometheus and grafana; thirteen containers if ai-triage's consumer runs as its own Compose service (spike item 7). The **database host** runs MySQL, Garage (bucket `bmc-attachments`), `mysqld_exporter` and the backup cron job; the **backup host** runs a second Garage (bucket `bmc-backups`). The design excludes a Kubernetes commitment. The hosts are not yet known (college servers are expected for the application host; placement and provider of the database and backup hosts are not chosen either; EN01-U3, Martim); the system should run on any Docker host. NFR-08 requires reproducible builds, containers, CI and configuration without secrets in Git; NFR-09 an exercised backup and restore. Docker's documentation calls a single server the easiest way to deploy with Compose (E59). Assignment §6.7 asks for logs, health, metrics, correlation, error reporting and a dashboard (E01).

## Alternatives

| Option | Benefits | Costs/risks | Evidence |
|---|---|---|---|
| **A. Host-agnostic contract: multi-arch images in GHCR + one Compose file on any Docker host** (chosen) | Same images and application-host Compose file on laptops, a college server, a VPS or an arm64 VM (a laptop also runs the database-host set, definition open); failure injection is easy; no provider lock-in | The application host and the database host are single points of failure; three hosts to patch; backups are self-managed; memory unknown until measured | E59 |
| B. Render free tier | Managed, free | Free services spin down after 15 minutes idle | E60 |
| C. Fly.io | Managed containers | Trial only | E60 |
| D. Railway | Managed | One-time USD 5 trial | E60 |
| E. Kubernetes | Standard orchestration | Not committed in the design; operational burden | [design §7](../07-technical-design.md#7-proposed-deployment-and-operations) |

B–D are rejected on the free-tier terms recorded in E60 (idle spin-down, trials only); in addition the stack contains Keycloak (about 1250 MB base memory, E28), RabbitMQ and MySQL, and its fit on those plans was not tested. Oracle Always Free (Ampere A1, arm64, 2 OCPUs / 12 GB, E60) remains a possible host under A, not a separate option.

## Proposed decision (not accepted)

**A**, proposed, not accepted.

**Edge.** Traefik 3.7 (v3.7.16, E34) is the only exposed container (80/443). Routes and middlewares:

| Route | Upstream | Middlewares |
|---|---|---|
| `/` | client nginx (static files) | Headers |
| `/api/issue/*`, `/api/dispatch/*`, `/api/notifications/*` | the matching Spring service, which serves service-relative paths | OIDC (traefik-oidc-auth plugin, `UnauthenticatedBehavior: Unauthorized`), StripPrefix (`/api/<service>`), RateLimit, Headers |
| The plugin's callback, login and logout paths (defaults `/oidc/callback` and `/logout`, login URI optional in the plugin but set in this design, because it is the only way to start the login; exact paths a spike detail) | none: the OIDC middleware answers them itself | OIDC auth (traefik-oidc-auth plugin), RateLimit, Headers |
| `/auth/*` | Keycloak | RateLimit, Headers |

The public `/status` page and the `/status/api` route proposed on 2026-10-27 were fed by Gatus; they are deferred past the MVP with the status page ([ADR-012](ADR-012-health-and-status-page.md)). Never route the Traefik API (E74). Internal endpoints (liveness and readiness endpoints, other Actuator endpoints, `/metrics`, the AI service's `/classify`, the simulator's control endpoint, RabbitMQ management, Garage, Mailpit) are never routed. Mailpit stays internal only; in the demo the presenter shows its inbox through an SSH tunnel (demo only). There is no JWT or OIDC middleware in Traefik Proxy (Traefik Hub only, E35), so the OIDC middleware is the community plugin traefik-oidc-auth (E88), loaded through Traefik's experimental plugin system (E89); each Spring service still validates the JWT itself ([ADR-005](ADR-005-authentication-authorisation.md)). Which Keycloak paths must stay unrouted (admin console), how Grafana is reached in demo, and the TLS certificate source are open items to settle with Martim.

**Containers.** On the application host: Traefik with the traefik-oidc-auth plugin (version pinned; v0.22.0 is the latest release, E88), Keycloak 26.8, RabbitMQ 4.x (pin a minor at the spike), Mailpit 1.32 ([ADR-007](ADR-007-notification-service.md)), Prometheus 3.x, Grafana 13, client nginx, Issue, Dispatch, Notification, `ai-triage` and the calendar simulator `calendar-sim` ([ADR-006](ADR-006-calendar-simulator.md)). On the database host: MySQL 8.4, Garage 2.5 with the bucket `bmc-attachments` ([ADR-010](ADR-010-object-storage.md)) and `mysqld_exporter`, which exposes MySQL metrics (image and version not yet recorded). On the backup host: Garage 2.5 with the bucket `bmc-backups`. There is no oauth2-proxy container ([ADR-005](ADR-005-authentication-authorisation.md)). `ai-triage` is one service at the same level as Issue, Dispatch and Notification: one image running two processes, the Flask web process and the pika consumer process; whether they run as one container or as two Compose services from the same image is spike item 7 ([ADR-008](ADR-008-ai-triage-service.md)). Gatus is not in the MVP ([ADR-012](ADR-012-health-and-status-page.md)). Only `ai-triage` (its AI provider) and Dispatch (the Google Calendar API, [ADR-006](ADR-006-calendar-simulator.md)) need outbound access; they get it through the `egress` network below. An egress proxy with an allow-list is not adopted for the MVP; it stays open for EN-01-04 (security review).

**Database and backup hosts.** One MySQL 8.4 instance with one database per service (`issue`, `dispatch`, `notification`, `keycloak`), each with its own user. Scaling a service adds replicas of that service, never another database; the instance scales vertically (a bigger machine). MySQL and Garage (`bmc-attachments`) run on a second machine, the database host; the nightly backups go to a Garage instance on a third machine, the backup host (runbook below). The services reach MySQL (TCP) and Garage (S3 API) over a **private link** between the application host and the database host. How that link is built (provider network, VPN, firewall rules), how the database host reaches the backup host, and how the containers on those two hosts are defined and started are open (spike, DEVOPS-02, Martim).

**Networks.** Three networks on the application host, where no port is published except Traefik's, plus the private link to the database host.

| Network | Members | Purpose |
|---|---|---|
| `edge` | Traefik, client, Issue, Dispatch, Notification, Keycloak | Traefik and the containers it routes to (Keycloak for `/auth/*`) |
| `internal` | Issue, Dispatch, Notification, Keycloak, ai-triage, calendar-sim, RabbitMQ, Mailpit, Prometheus, Grafana | Broker, mail capture (Keycloak joins for its verification email), metrics and the simulator |
| `egress` | ai-triage, Dispatch | The only way out to the internet: the AI provider and the Google Calendar API |
| Private link to the database host | Issue, Dispatch, Notification and Keycloak to MySQL; Issue to Garage's S3 API; Prometheus to `mysqld_exporter` and Garage's metrics (not yet specified, P-08) | Databases and attachment storage; MySQL, Garage and the exporter are reachable only over it |

How `edge` and `internal` are kept from reaching the internet in Compose, and which network carries the services' traffic to the private link, are confirmed at the spike with Martim.

**Images and Compose.** Images for each app in GitHub Container Registry for linux/amd64 and linux/arm64. One `compose.yaml` for the application host with profiles (names proposed): `core` (seven containers there, plus MySQL on the database host, below); `observability` (Prometheus and Grafana: standard in demo and release, optional on a laptop); `demo` (synthetic realm users only, [ADR-005](ADR-005-authentication-authorisation.md)). MySQL, Garage and `mysqld_exporter` on the database host, and Garage on the backup host, are defined outside that Compose project; how is open (DEVOPS-02). The `storage` profile proposed earlier now means Garage on the database and backup hosts. On a laptop or in CI one machine runs everything, MySQL and Garage included; how that local set is defined is open (DEVOPS-02), and `storage` names Garage in that local set and on the database and backup hosts, not a profile of the application host's project. ai-triage, Notification and calendar-sim are added when the slice needs them. `.env.example`; secrets only in the host or CI environment, never in Git. Multi-arch availability is recorded for Traefik, RabbitMQ, MySQL, Mailpit, Temurin and python images (E08, E23, E34, E37, E44, E52); it is not checked for Keycloak, Garage, `mysqld_exporter`, Prometheus, Grafana or nginx, so spike item 8 covers both architectures.

**Minimal profile for the first vertical slice (proposal, to decide at the team review, EN01-U1).** The Sprint 2 slice is not yet defined in the repository; this proposal assumes a resident reports a fault through the client and an administrator sees and handles it through Issue and Dispatch (two independent backend components, [walking skeleton](../10-walking-skeleton.md)). The team can start from a smaller set and add containers as stories need them; the design of the later ones stays as written above. Reviewers can change the assumption and the split.

| When | Containers | Reason |
|---|---|---|
| First (`core`: seven containers on the application host, plus MySQL on the database host) | Traefik, Keycloak, RabbitMQ, Issue, Dispatch, client nginx, Mailpit on the application host; MySQL on the database host, defined outside the application host's Compose project | Sign-in and the Backend-for-Frontend session in Traefik ([ADR-005](ADR-005-authentication-authorisation.md)) are needed by every journey; Issue and Dispatch exchange events through the broker (membership and issue-state projections, [ADR-003](ADR-003-asynchronous-messaging-rabbitmq.md)). Keycloak's verification emails need SMTP from the first journey, so Mailpit is in `core` (internal only, never routed) |
| When the slice includes the step | ai-triage; Notification service; calendar simulator | Reporting works with AI disabled and manual triage is always possible (NFR-03, [ADR-008](ADR-008-ai-triage-service.md)), so triage can follow. The Notification service also hosts the in-app channel ([ADR-007](ADR-007-notification-service.md)), so it is needed as soon as US-10 notifications are in the slice, even without email. The simulator is needed when Dispatch books a visit in tests or failure demos ([ADR-006](ADR-006-calendar-simulator.md)) |
| Later | Prometheus and Grafana; Garage on the database host; the backup host | Prometheus and Grafana are the `observability` profile. Garage on the database host serves the report-photos candidate (post-MVP, pending a DEC entry); the backup host (Garage, `bmc-backups`) receives the nightly dumps, so it is needed before the backup and restore exercise (NFR-09) ([ADR-010](ADR-010-object-storage.md)) |

Later containers would join through further profiles (`observability` on the application host; `storage` as above; the `status` profile proposed earlier disappears with Gatus) so that a laptop starts only the set the slice uses. Memory of the minimal profile, as of the full stack, is not measured (EN01-U3); spike item 8 should record both.

**Pipeline (outline; no CI exists yet).** Aligned with PR #40 (E02, proposed, open, not merged): `feature/* → dev → main`, release by protected `v*` tag, build once and promote the same image. Proposed stages: lint → unit tests → `buf lint` and `buf breaking` → boundary tests ([ADR-009](ADR-009-service-internal-architecture.md)) → integration tests with real MySQL 8.4 and RabbitMQ containers → multi-arch build and push to GHCR. Deployment is `docker compose pull && docker compose up -d`. Required checks are configured only when the pipeline exists; arm64 build method (emulation or native runners) is open (EN01-U9).

**Health checks and startup order.** Every BMC service exposes liveness and readiness endpoints, names per [DEVOPS-02 (#42)](https://github.com/Phenriquerafael/LABDSOF_G9A/issues/42); they are internal and never routed publicly. Container health checks, Traefik `loadBalancer.healthcheck` on readiness, startup order with `depends_on: condition: service_healthy` and the Prometheus `up` alerts are specified in [ADR-012](ADR-012-health-and-status-page.md) (E73, E74, E77–E79); this ADR does not repeat them.

**Observability.** Prometheus scrapes each service's metrics endpoint (Actuator/Micrometer, Flask `prometheus_client`), RabbitMQ and Traefik (E36, E39, E58). It would also scrape `mysqld_exporter` and Garage's metrics on the database host over the private link; that path is not yet specified and Garage's metrics endpoint is not verified, so both stay open (P-08 of the [physical views](../07b-physical-views.md), Martim with Ricardo); the per-target `up` series and alerts on it cover a service that has gone; blackbox_exporter is added only if readiness endpoints must be probed directly ([ADR-012](ADR-012-health-and-status-page.md)). Grafana remains the operator dashboard and the §6.7 dashboard; Gatus and the public status page are deferred past the MVP ([ADR-012](ADR-012-health-and-status-page.md)). The Grafana dashboard shows outbox lag, DLQ depth, consumer retries, AI fallback rate, pending bookings, error rate, notification failures and projection freshness. Correlation uses W3C `traceparent` and `correlationId` (CloudEvents extensions and HTTP headers). Traefik writes JSON access logs but has no built-in request-ID generator (E36), so the first Spring service generates a missing correlation ID (to confirm in the spike). Loki and Tempo are left to DEVOPS-02 (Martim, EN01-U12).

**Runbook.** Start/stop, logs, migrations, rollback to the previous image tag, **DLQ replay** (management-UI shovel back to the source queue; [ADR-003](ADR-003-asynchronous-messaging-rabbitmq.md)), **projection rebuild** (Issue's snapshot job republishing memberships and issue states for Dispatch; [design §4.3](../07-technical-design.md#43-how-dispatch-obtains-trustworthy-authorisation-context)), and **backup and restore**, kept simple for the academic release: a cron job on the database host (not a container) runs a nightly `mysqldump` of each database into the Garage bucket `bmc-backups` on the backup host ([ADR-010](ADR-010-object-storage.md)), using a read-only MySQL backup user and the `bmc-backups` key, both in the database host's environment; restore is exercised once with counts and integrity checks (NFR-09). No snapshot scheme. Single-node Garage has no redundancy (E46), but the backups sit on a third machine, outside the database host's failure domain, so losing the database host does not lose them. An off-host copy to Cloudflare R2 (E49) is no longer needed for the academic release; it stays an optional alternative target ([ADR-010](ADR-010-object-storage.md)).

**Hosts.** College servers are expected for the application host, not confirmed; placement and provider of the database and backup hosts are not chosen either (EN01-U3, Martim); the contract does not depend on the choice.

## Consequences

- No provider lock-in; a reviewer can run the system from a clone once the local set for MySQL and Garage is defined (DEVOPS-02).
- **Memory is the main risk.** Three Spring JVMs, the simulator JVM, Keycloak (about 1250 MB base, E28), RabbitMQ (high watermark 0.6 of RAM, E39), Prometheus and Grafana together on the application host are likely several GB; MySQL and Garage now load the database host instead. This is not measured; it is measured in the spike on the real host and architectures, and may force profile or sizing changes (the minimal profile above is the first lever).
- The application host, the database host (one MySQL instance), the private link between them and one RabbitMQ node are single points of failure, stated as limits of the academic release ([ADR-001](ADR-001-backend-boundaries.md)); losing the backup host loses only the backups. Three hosts must be provisioned and patched instead of one.
- Multi-arch builds lengthen CI; this proposal takes that cost to keep the host choice open.
- More secrets to manage (Keycloak client secrets, the edge plugin's 32-character session `Secret`, per-service database and broker credentials, the Google Calendar credentials, and on the database host the backup user and the `bmc-backups` key); rotation is EN01-U6.
- Dispatch and ai-triage reach the internet through `egress` without an allow-list; whether to add an egress proxy is an EN-01-04 item.

## Verification and review

Spike item 8 (measured memory of the full stack on amd64 and arm64), items 1, 3 and 5 (Keycloak, the edge OIDC plugin, dead-lettering) and the private link (DEVOPS-02) feed this ADR; items 11 and 12 (Gatus) are deferred with the status page ([ADR-012](ADR-012-health-and-status-page.md)). Before release: fresh clone → database and backup hosts started → `docker compose up` on the application host → guided journey works; backup/restore exercise recorded; a DLQ replay rehearsed; stopping the simulator, then a service, then the broker shows the degraded modes expected by §6.8, in context in the client (booking pending or calendar unavailable, “triage pending — classify manually”, delayed email) and in Grafana. Review when the host is chosen and at Sprint B planning (EN01-U10 version re-check).
